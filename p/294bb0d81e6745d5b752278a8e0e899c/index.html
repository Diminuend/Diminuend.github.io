告别本地NAS：利用 GitHub Actions + rclone 打造 Joplin 零成本全自动异地容灾备份

发表于2026-08-20|更新于2026-08-20|杂项知识
|浏览量:

1. 背景与目标

1.1 痛点背景

Joplin 是一款支持端到端加密（E2EE）的优秀开源笔记软件，通常配合 WebDAV（如 InfiniCloud、坚果云、自建 Nextcloud）实现多端数据同步。为了防止 WebDAV 服务商单点故障或误删数据，通常需要对数据进行第二重冷备份。

  • 旧方案：依赖家里常驻运行的 Docker / NAS 机器，定时拉取 WebDAV 数据到本地，再通过脚本 Push 到 GitHub 私有仓库。
  • 存在问题：强依赖家庭网络、公网 IP/内网穿透以及常驻开机硬件，一旦断电、断网或容器异常，备份就会中断，维护成本较高。

1.2 改造目标

  • 纯云端无服务器化（Serverless）：不依赖任何本地硬件与常驻服务器。
  • 智能增量备份：只同步变动文件，无变动不产生无意义的 Commit。
  • 分时段智能调度：工作活跃时段高频备份（每 1 小时），夜间低频备份（每 4 小时）。
  • 兼容 E2EE 加密与超大附件：在开启 Joplin 端到端加密的情况下，兼顾大附件（>100MB）突破 GitHub 限制，同时绝不滥用 Git LFS 免费配额。

2. 整体架构与工作流

整个备份流程由 GitHub Actions 定时触发，利用 rclone 增量拉取 WebDAV 数据，经过大文件动态嗅探后，自动提交至 GitHub 私有仓库：

flowchart TD
    A[GitHub Actions 定时 Cron 触发] --> B[拉取当前 GitHub 仓库与 LFS 环境]
    B --> C[极速安装 rclone 依赖]
    C --> D[注入 Secrets 并动态混淆 WebDAV 密码]
    D --> E[rclone sync 增量拉取 InfiniCloud 到 notes_content]
    E --> F{扫描是否存在 >80MB 的超大文件?}
    F -- 是 --> G[动态执行 git lfs track 仅将大文件加入 LFS]
    F -- 否 --> H[全部文件走普通 Git 存储, 节省 LFS 配额]
    G --> I{检测 notes_content 目录是否有文件变动?}
    H --> I
    I -- 有变动 --> J[以北京时间生成 Commit 并 Push 到仓库]
    I -- 无变动 --> K[跳过提交, 任务静默结束]

3. 详细落地步骤

步骤一：在 GitHub 私有仓库配置 Secrets

进入 GitHub 仓库 Settings -> Secrets and variables -> Actions -> New repository secret，添加 WebDAV 凭据：

  • WEBDAV_URL：https://soya.infini-cloud.net/dav/Joplin/（包含子路径）
  • WEBDAV_USER：WebDAV 账号
  • WEBDAV_PASS：WebDAV 密码（支持明文）

步骤二：开启 Workflow 写入权限

进入 GitHub 仓库 Settings -> Actions -> General，滚动到最下方 Workflow permissions，选择 Read and write permissions 并保存。

4. 踩坑记录与关键解决方案

在实践过程中遇到了若干典型问题，以下为具体复盘与解决方式：

坑 1：Ubuntu 环境下 apt-get update 超时卡死

  • 现象：Action 卡在 sudo apt-get update 阶段数分钟无响应。
  • 原因：Azure / Ubuntu 官方源偶发网络抖动；同时 GitHub Actions 镜像本身已预装 git-lfs。
  • 解决：跳过 apt-get，直接使用 rclone 官方脚本 curl https://rclone.org/install.sh | sudo bash 进行安装，耗时由数分钟缩短至 3 秒。

坑 2：rclone 报错 couldn't decrypt password

  • 现象：运行时报错 CRITICAL: Failed to create file system for "mywebdav:": couldn't decrypt password: input too short when revealing password。
  • 原因：rclone 环境变量 RCLONE_CONFIG_<NAME>_PASS 强制要求传入混淆后的密码字符串（Obscured Password），直接传入明文会被误当成损坏的密文尝试解密。
  • 解决：在 Bash 脚本中动态调用 OBSCURED_PASS=$(rclone obscure "$WEBDAV_PASS") 自动转换，用户在 GitHub Secrets 中继续保存普通明文密码即可。

坑 3：Joplin 端到端加密（E2EE）导致常规 LFS 规则失效

  • 现象：开启 E2EE 后，所有文件被加密为无后缀或随机哈希命名（如 39f7a6c90b8e...），原本通过扩展名（*.pdf、*.mp4）匹配 Git LFS 的规则全部失效。
  • 矛盾点：如果粗暴地将 .resource/* 整个目录全部交给 LFS，又会导致大量几 KB 的小图片碎片迅速耗尽 GitHub 免费提供的 1 GB LFS 存储上限。
  • 优雅解法：清空所有预设规则，在 Commit 前使用 find notes_content -type f -size +80M 动态扫描。只有真实体积超过 80MB 的加密大附件才会被临时抓取并执行 git lfs track，其余 99% 的加密小文件全部存放在普通 Git 仓库中。

坑 4：git add .gitattributes 抛出 128 异常

  • 现象：报错 fatal: pathspec '.gitattributes' did not match any files。
  • 原因：在日常没有超过 80MB 文件的情况下，git lfs track 不会执行，仓库内并不存在 .gitattributes 文件，强制 git add 会报错退出。
  • 解决：使用条件判断 if [ -f .gitattributes ]; then git add .gitattributes; fi，实现平滑容错。

6. 方案收益总结

  1. 0 运维成本：彻底关停本地常驻 Docker 备份脚本，无需担心停电、断网。
  2. 0 资金成本：GitHub 私有仓库每月赠送 2000 分钟 Action 配额，增量备份单次耗时约 10~20 秒，每月累计消耗不足 150 分钟。
  3. 高安全性与高可用：数据双重加密隔离（Joplin E2EE 加密 + GitHub 私有仓库权限 + Secrets 安全托管），形成标准且坚固的异地灾备体系。
